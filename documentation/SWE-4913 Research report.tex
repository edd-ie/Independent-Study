	\section{High Performance Parallelism}
	\label{sec:background}
	\subsection{Message Passing Interface (MPI)}
	Industry standard specification used for communication between processes in parallel computing
	\\\\MPI attempts to solve the following problems:
	
	\begin{itemize} 
		\item \textbf{Portability:}
		\\Each vendor had propriety library for message passing thus requiring rewrites for different use cases.\\
		\\\textbf{Solution} - MPI provides a standard API provided an MPI is installed (OpenMPI, MPICH)
		
		\item \textbf{Memory wall (\textit{Distributed Memory Management}):}
		\\Most large scale computers are distributed memory systems. Moving data between isolated memory manually is complex and error-prone.\\
		\\\textbf{Solution} - MPI treats communication as explicit messages. MPI uses objects called \textit{communicators} 
		and \textit{groups} to define which collection of processes may 
		communicate with each other.\\
		Provides functions that handle networking, buffering and memory copying.
		\begin{itemize}
			\item\textbf{Sender}: A process calls \textit{MPI\_Send()} (or a variant) to transmit a message.
			\item\textbf{Receiver}: A process calls \textit{MPI\_Recv()} to accept the message.
			\item\textbf{Message Envelope}: Data buffer (address, type, count), Sou5rce/destination ranks, Message tag, Communicator (\textit{MPI\_COMM\_WORLD} by default)
		\end{itemize}
		
		\item \textbf{Complexity of collective operations:}
		\\ Parallel algorithms often send pieces of data or collects results from multiple end points. 
		\\Writing \textit{one-to-many} or \textit{many-to-one} patterns is tedious and usually inefficient.
		\\\\\textbf{Solution} - MPI provides collective communication through built in functions.
		\begin{itemize}
			\item \textbf{Broadcaster} - sends data from one process to all.
			\item \textbf{Scatter/Gather} - Splitting a large vector into chunks for different processes or reassembling them.
			\item \textbf{Reduction} -  performing calculations across all processors and return a single result.
		\end{itemize}
		
		\item \textbf{Hardware heterogeneity:}
		\\Computing clusters consists of different machines with different architecture e.g \textit{big/little endian}.
		\\\textbf{Solution} - MPI uses opaque datatypes and handles translation between different machines e.g. \textit{(4, MPI\_INT) a vector with 4 integer values}
		
	\end{itemize}
	
	\subsubsection{The OpenMPI Architecture}
	OpenMPI is base on the Modular Component Architecture is a system that breaks down a software into independent, interchangeable modules, each encapsulating specific functionality. It is a series of projects, frameworks, components, and modules that are assembled at run-time to create an \textit{MPI} implementation.
	\\Each framework typically has one or more components that are used at run-time. \textbf{Point-to-point Management} Layer sits between the \textit{MPI} API and the lower-level network transport layers. It manages message matching, ordering, and delivery guarantees required by the MPI standard. It decides how and through which transport a message will be sent. The \textbf{ucx} \textit{pml} sends messages across \textbf{InfiniBand-based networks}. 
	\\The \textbf{btl} framework is used by the MPI layer to send bytes across different types underlying networks. The \textbf{tcp} \textit{btl}, for example, sends messages across TCP-based networks
	
	\subsubsection{Communication Protocols}
	MPI provides three different communication methods that MPI processes can use to communicate with each other.
	
	\begin{itemize}
		\item \textbf{Point-to-Point Communication} - the most used communication method. It involves the transfer of a message from one process to a particular process in the same communicator. MPI provides blocking (\textit{synchronous}) and non-blocking (\textit{asynchronous}) point-to-point communication. 
		\\For the \textit{blocking} communication, an MPI process \textit{sends a message to another MPI process and waits until the receiving process completely and correctly receives the message} before it continues its work. 
		\\On the other hand, a sending process using \textit{non-blocking} communication \textit{sends a message to another MPI process and continues its work without waiting} to ensure that the message has been correctly received by the receiving process.
		
		\item \textbf{Collective Communication} - a process broadcasts a message is to all processes in the same communicator including itself.
		
		\item \textbf{One-sided communication} - a process can directly access the memory space of another process without involving it.
	\end{itemize}
	
	\newpage
	\begin{lstlisting}
		/* Standard send in MPI. Behind the scenes, it will issue a buffered send MPI_Bsend or a synchronous send MPI_Ssend, based on whether the buffer attached contains enough free space for the message. */
		int MPI_Send(const void* buffer, int count, MPI_Datatype datatype, int recipient, int tag, MPI_Comm communicator);
		
		/* Asynchronous blocking send ('B' == buffered); it will block until a copy of the buffer passed is made. MPI will send the buffer copied at a later point */ 
		int MPI_Bsend(const void* buffer, int count, MPI_Datatype datatype, int recipient, int tag, MPI_Comm communicator);
		
		/* Synchronous blocking send; it will block until the recipient has received the message. Ensure the buffer and be used safely once MPI_Ssend return */
		int MPI_Ssend(const void* buffer, int count, MPI_Datatype datatype, int recipient, int tag, MPI_Comm communicator);
		
		/* Standard blocking send ('R' == ready); it will block until the recipient has received the message. Requires the recipient to have issued the corresponding receive routine (MPI_Recv or MPI_Irecv) before MPI_Rsend is invoked. */
		int MPI_Rsend(const void* buffer, int count, MPI_Datatype datatype, int recipient, int tag, MPI_Comm communicator);
		
	\end{lstlisting}

	\subsection{Resumable / Partial Downloads}
	
	Partial or resumable downloads allow a client to retrieve only specific portions of a resource rather than downloading the entire file from the beginning. This is essential for large media files, software packages, and any scenario where network interruptions are common.  
	To support partial downloads, the \textbf{server (sender)} must explicitly implement HTTP range semantics and advertise that it can return byte ranges on demand.
	
	\subsubsection{Range}
	
	The \texttt{Range} header specifies which segment(s) of a resource the client wants to retrieve.  
	It enables efficient skipping, seeking, and resuming of downloads without re-fetching previously received data.
	
	\textbf{Relevant status codes:}
	\begin{itemize}
		\item \textbf{206 Partial Content} — The server supports range requests and is returning the requested segment(s).
		\item \textbf{416 Range Not Satisfiable} — The requested range is invalid (e.g., out of bounds).
		\item \textbf{200 OK} — The server does not support range requests or has chosen to ignore the header.
	\end{itemize}
	The header can request one or multiple subranges, similar to how media players jump to different timestamps in audio or video streams.
	
	\begin{lstlisting}
		Range: <unit>=<start-end>
		Range: <unit>=<n->        // from byte n to the end
		Range: <unit>=<-n>        // last n bytes of the file
		Range: <unit>=<s-e>, <s-e>, <s-e>   // multiple non-contiguous ranges
		Range: <unit>=<s-e>, <-e>           // mixed range types
	\end{lstlisting}
	Servers may return ranges in sequential order even if the client requested them out of order, ensuring efficient streaming without buffering the entire response.
	
	\subsubsection{Accept-Range}
	The \texttt{Accept-Ranges} header indicates whether the server supports range requests and which unit it accepts (typically bytes).
	
	\begin{lstlisting}
		Accept-Ranges: none
		Accept-Ranges: bytes
	\end{lstlisting}
	If the server returns \texttt{none}, clients should fall back to full downloads.
	
	\subsubsection{Content-Range}
	The \texttt{Content-Range} header describes where the returned segment fits within the full resource.  
	It is included in responses with status \textbf{206}.
	
	\begin{lstlisting}
		Content-Range: <unit> <range>/<size>   // e.g. bytes 0-499/2000
		Content-Range: <unit> <range>/*        // size unknown
		Content-Range: <unit> */<size>         // 416: invalid range
	\end{lstlisting}
	This header allows clients to:
	\begin{itemize}
		\item reconstruct the full file from multiple partial responses,
		\item verify progress,
		\item detect mismatches or corruption.
	\end{itemize}
	
	\subsubsection{If-Range}
	The \texttt{If-Range} header makes a range request conditional.  
	If the resource has not changed since the client last downloaded it, the server returns \textbf{206}.  
	If it has changed, the server returns \textbf{200} with the full resource, ensuring the client does not stitch incompatible segments together.
	\\\\
	The header may use either:
	\begin{itemize}
		\item \textbf{Last-Modified} timestamp, or
		\item \textbf{ETag} value
	\end{itemize}
	but not both simultaneously.\\\\
	This mechanism is crucial for safe resumable downloads, especially when files may be updated on the server.

	\subsection{Resumable / Multipart Uploads}
	Resumable or multipart uploads are designed to reliably transfer large files over unstable or bandwidth‑limited networks. Instead of sending the entire file in a single request, the file is divided into smaller, manageable chunks that are uploaded independently. This approach improves reliability, reduces memory usage, and allows uploads to continue even after interruptions.
	\\
	\textbf{Resumability} is achieved by tracking which chunks have been successfully acknowledged by the receiver.  
	If a failure occurs—whether due to network instability, client crash, or server timeout—the sender retransmits only the missing chunks rather than restarting the entire upload.
	
	\subsubsection{Stages}
	
	\textbf{Initiation}  
	The sender begins by issuing a POST request to the receiver to start an upload session.  
	The receiver responds with a unique \textit{upload-id} and allocates temporary storage for incoming parts. This identifier is used to associate all subsequent chunk uploads with the same file.
	\\\\
	\textbf{Part Upload}  
	The file is sliced into fixed‑size or dynamically sized chunks. Each chunk is uploaded independently along with its \textit{part-number} and the \textit{upload-id}.  
	Because each part is isolated, uploads can be parallelized and retried individually.
	\\\\
	\textbf{Finalization}  
	Once all parts have been successfully uploaded, the sender issues a completion request containing the list of all \textit{Etags} (hashes or identifiers returned by the receiver for each part).  
	The receiver verifies the list, stitches the chunks together in the correct order, performs integrity checks, and returns a final confirmation.
	
	\subsubsection{Advantages}
	
	\textbf{Parallel Streams:}\\ 
	The sender can open multiple concurrent HTTP connections (typically 4–8) to upload different chunks simultaneously. This maximizes throughput and better utilizes available bandwidth.\\
	\\
	\textbf{Memory Efficiency:}\\  
	Only small slices of the file need to be loaded into memory at any given time. This avoids the overhead of buffering large files and keeps RAM usage predictable and low.\\
	\\
	\textbf{Error Isolation:} \\
	Failures affect only the chunk being uploaded. Instead of restarting the entire transfer, the sender retries only the failed part, significantly reducing wasted time and bandwidth.
	
	\subsubsection{Best Practices}
	\textbf{Exponential Backoff} - When a chunk upload fails, the sender should not retry immediately. Instead, it waits progressively longer intervals (e.g., 1s → 2s → 4s) before retrying.This prevents unnecessary congestion and aligns with common network‑friendly retry strategies.\\	
	\\
	\textbf{MD5 Validation} - Each part should include an MD5 checksum header. The receiver validates the checksum before acknowledging the upload, ensuring data integrity and preventing corrupted chunks from being accepted.\\
	\\
	\textbf{Cleanup Process} - Unfinished or abandoned uploads can accumulate over time. Lifecycle rules should be configured to automatically delete incomplete uploads after a defined retention period.\\
	\\
	\textbf{Dynamic Chunking} - Chunk size can be adapted based on network conditions, example:  
	\begin{itemize}
		\item \textit{5 MB} chunks for mobile or unstable networks  
		\item \textit{25 MB} chunks for high‑speed fibre connections  
	\end{itemize}
	This improves reliability and reduces the likelihood of chunk‑level failures.

	\subsection{Latency}
	Time it takes for data to go from the origin to the destination. This delay encompasses various factors such as:
	\begin{itemize}
		\item \textbf{Processing delay} - time it takes for data to be processed by network devices like routers \& switches
		\item \textbf{Queueing delay} - time spent in queue waiting to be processed by the to the destination host.
		\item \textbf{Transmission delays} - time it takes to push the packet’s bits into the wire.
		\item \textbf{Propagation delays} - time the signal takes to propagate through the medium. It would be a signal through an optic cable.
	\end{itemize}
	It refers to network’s responsiveness and perceived speed and it is measured in milliseconds. The lower the "latency time" in milliseconds the better

	\subsubsection{Calculations}
	
	\begin{flushleft}	
		\[
		\begin{aligned}
			\text{Packet size } (L) &= \text{Packet size} \\
			\text{Average rate of arrival } (a) &= \frac{\text{packets}}{\text{sec}} \\
			\text{Bandwidth } (R) &= \frac{b}{\text{sec}} \\
			\text{Traffic intensity} &= L \cdot \frac{a}{R} \\
			\text{Propagation delay } (d_{\text{prop}}) &= \frac{m}{s} \\
			\text{Transmission delay } (d_{\text{trans}}) &= \frac{L}{R} \\
			\rho &= \frac{1}{R} \\
			\text{Time of 1st bit arrival (ms)} &= d_{\text{prop}} + \rho
		\end{aligned}
		\]
	\end{flushleft}

	\subsection{Jitter}
	The measure of the variation of latency over time, measured in \textit{milliseconds}. It is the measure of the variability in packet arrival times, which can be caused by:
	\begin{itemize}
		\item \textbf{Network congestion}: High traffic volumes causing packets to take longer paths or experience delays.
		\item \textbf{Routing Changes}: Dynamic changes in the path that data packets take across the network.
		\item \textbf{Variable Path Lengths}: Differences in the physical distance data packets must travel.
		\item \textbf{Equipment Limitations}: Older routers with limited processing power struggle to handle modern network traffic volumes. When a router's buffer fills up, it must decide which packets to prioritize and which to delay or drop entirely.
	\end{itemize}
	It affects the quality of real-time communication. If the jitter is high then it may cause packet loss, poor audio and video quality transmission, and data streaming interruptions.Thus, jitter is a significant objective to consider in the performance of networks serving real-time applications.

	\subsection{Data Processing Paradigm}
	Data processing plays a role in how efficiently and effectively a system handles varying loads.\\
	\\\textbf{CAP theorem:} distributed systems can guarantee at most two out of three properties [\textit{Eric Brewer, 2000}]
	\begin{itemize}
		\item \textbf{Consistency} -  every read receives the most recent read or an error. All clients sees the same data at same time no matter which node they connect to. For this to work data written to one node must be instantly forwarded \& replicated in all other nodes before a write is deemed successful.
		\item \textbf{Availability} - every request by a non-failing node must result in a response, without a guarantee it has the most recent version of data.
		\item \textbf{Partition tolerance} - system continues to operate despite an arbitrary number of messages being dropped/delayed by the network between nodes. In case of a \textit{network partition} failure it must be decided whether:
		\begin{itemize}
			\item Cancel the operation, decreasing availability but ensuring consistency.
			\item Proceed with the operation, providing availability but risk inconsistency.
		\end{itemize}
	\end{itemize}	
	\textbf{Network partition} - division of a computer network into relatively independent subnet either by design to optimize them separately or due to failure of network devices. Distributed software should be partition-tolerant that is even after a network is partitioned, it should still work.

	\subsubsection{Batch Processing}
	Aggregation of data into discrete groups and processing them in a single scheduled operation, typically offline, triggered by time intervals (\textit{e.g. nightly jobs}) or data thresholds (\textit{e.g. 1GB patches}).\\
	Ideal for:
	\begin{itemize}
		\item \textbf{Data warehousing} - central storage of data from multiple sources.
		\item \textbf{Extract Transform Load (\textit{ETL})} - collection of data from a source reshaping/processing it and moving it to an output.
		\item Large scale reporting
	\end{itemize}
	There are a variety of \textit{ETL} tools for batch processing: \textit{Apache airflow, Hadoop, AWS Data pipeline, Oracle data integration}.\\
	\\Core steps:
	\begin{itemize}
		\item \textbf{Data collection:}\\Accumulation of data from sources into storage le \textit{S3, HDFS}.
		\item \textbf{Processing:}\\Execute computation/transformation on an entire batch.
		\item \textbf{Error handling:}\\Retries on batch failures, with \textit{idempotency} ensuring repeated runs don't duplicate outputs (\textit{use of unique-ids like snowflakes for batch identifiers})
	\end{itemize}
	
	\begin{flushleft}	
		\[
		\begin{aligned}
			\text{Throughput} &= \frac{\text{batch size}}{\text{processing time}} \\
			\text{Latency} &= \text{Batch interval} + \text{processing time} \\
			\text{Resource utilization} &= \text{Peak usage during processing (\textit{e.g. 80\% CPU for 30min}), idle otherwise.}
		\end{aligned}
		\]
	\end{flushleft}
	\textbf{Fault tolerance} - use replication \textit{e.g. 3X HDFS} and heartbeats for node liveness, failure trigger job restarts from checkpoints.
	
	\subsubsection{Stream Processing}
	Handle and analyse data in real time or near real time as they arrive. Data streams are then processed as they arrive, involving a series of operations such as filtering, transforming and data aggregation. Allowing real-time implementations like; live analytics, triggering alerts, real-time dashboards.\\
	\\Core steps:
	\begin{itemize}
		\item \textbf{Data ingestion:}\\
		Consume events from sources like message queues using \textit{CDC} for database changes (\textit{e.g. Kafka topics})
		\item \textbf{Processing:}\\
		Apply transformations using frameworks (\textit{like Apache Flink or Kafka streams}).
		\item \textbf{Output:}\\
		Emit results to sinks (\textit{e.g. databases, caches}) in real-time.
		\item \textbf{Error handling:}\\
		Idempotency for safe retries (\textit{e.g. use unique\_ids}), rate limiting (\textit{e.g. token buckets}) to prevent overload and dead-letter queues for failed events.
	\end{itemize}
	\begin{flushleft}	
		\[
		\begin{aligned}
			\text{Throughput} &= \text{N} + \text{node throughput} \\
			\text{Latency} &= \text{ingress time} + \text{processing time}  + \text{egress time} \\
			\text{Resource utilization} &= \text{For aggregation, window (\textit{e.g. 5min}) affects memory (\textit{1GB for 1M events/window})}
		\end{aligned}
		\]
	\end{flushleft}

	\subsection{Software Environment}

	\subsection{Software Environment}
	The software stack was selected to ensure high-performance execution and minimal overhead during point-to-point data transfers. The environment is detailed as follows:
	
	\begin{itemize} 
		\item \textbf{Operating System:} The experiments were conducted on a Windows Subsystem for Linux running \texttt{Ubuntu 24.04.3 LTS} with the \textbf{Kernel version 6.6.87.2-microsoft-standard-WSL2}. To ensure maximum throughput, we verified that \texttt{sysctl} parameters for TCP/IP (such as \texttt{net.core.rmem\_max} and \texttt{net.core.wmem\_max}) were tuned to support large window sizes for high-bandwidth networks.
		
		\item \textbf{MPI Implementation:} We utilized \textbf{Open MPI v5.0.9}. The library was built against external \textbf{PMIx v5.0.9} and \textbf{PRRTE v3.0.12} dependencies to ensure a modern, modular process management layer. For intra-node communication within the WSL2 environment, the Modular Component Architecture (MCA) was verified to prioritize the \texttt{sm} (shared memory) and \texttt{self} Byte Transport Layers (BTL). This configuration enables low-latency, high-bandwidth data movement via shared memory regions, bypassing the network stack for local processes. Additionally, the \texttt{tcp} BTL was configured for management and coordination across the virtualized network interface.
		
		\item \textbf{Runtime Infrastructure:} To support the Open MPI 5.0 modular architecture, we deployed the \textbf{PMIx (Process Management Interface Exascale) v5.0.9} and \textbf{PRRTE (PMIx Reference RunTime Environment) v3.0.12} frameworks. These components were manually compiled and linked to provide a robust distributed process management layer, facilitating efficient process wire-up and synchronization during the \texttt{MPI\_Init} phase.
		
		\item \textbf{Compiler and Flags:} All C source files were compiled using the \textbf{GCC 14.2.0} suite. To achieve "wire-speed" performance and ensure the CPU does not become the bottleneck during data packing/unpacking, the following optimization flags were applied:
		\begin{itemize}
			\item \texttt{-O3}: Enables aggressive code optimizations including loop vectorization.
			\item \texttt{-march=native}: Instructs the compiler to generate instructions specific to the host CPU architecture.
